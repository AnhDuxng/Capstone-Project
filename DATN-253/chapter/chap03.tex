\subsection{Core Architectural Evolution}

As illustrated in Figure~\ref{fig:phase3-architecture}, the Phase 3 architecture reorganizes the credential lifecycle into a decoupled, unidirectional dataflow. Rather than transmitting raw claims through heavy intermediary protocols, the system isolates high-throughput cryptographic operations off-chain within the TypeScript SDK, committing strictly a 32-byte cryptographic root to \texttt{CredentialRegistryV3}. Concurrently, authority governance is delegated to an independent \texttt{IssuerRegistry}, establishing a clean separation of concerns between cryptographic identity management and cohort state anchoring.

\section{EIP-712 Credential Schema Design}

\subsection{BkCredential Type Definitions}

The EIP-712 type definition consists of a nested schema structure:

\begin{lstlisting}[language=Solidity]
struct PublicClaims {
    string vct;              // Verifiable Credential Type, e.g. "BKISC_DEGREE"
    string degreeTitle;      // e.g. "Bachelor of Computer Science"
    string graduationDate;   // ISO-8601: "2026-06-15"
    string honors;           // "High Distinction" | "Distinction" | ""
}

struct BkCredential {
    string         credId;         // URN UUID v4
    uint64         issuedAt;       // Unix timestamp in seconds
    string         batchId;        // e.g. "GRAD-2026-01"
    PublicClaims   publicClaims;   // Nested structured claims
    bytes32[]      privateClaims;  // Array of 32-byte salted commitments
    bytes32        merkleRoot;     // Batch Merkle root anchored on-chain
}
\end{lstlisting}

\subsection{Public and Private Claims Separation}

\begin{itemize}
    \item \textbf{PublicClaims}: Encapsulates verifiable public achievements that require no disclosure restrictions (\texttt{vct}, \texttt{degreeTitle}, \texttt{graduationDate}, \texttt{honors}).
    \item \textbf{PrivateClaims}: An array of \texttt{bytes32} hashes representing private individual claims (e.g., student name, ID, GPA, date of birth) protected by 256-bit salted commitments:
\end{itemize}

\begin{lstlisting}
privateClaims = [
    keccak256(abi.encode(salt_1, "fullName",  "Ho Anh Dung")),
    keccak256(abi.encode(salt_2, "studentId", "2052921")),
    keccak256(abi.encode(salt_3, "dob",       "2002-05-15"))
]
\end{lstlisting}

\subsection{Credential File Format}

The canonical output file distributed to the holder is a structured JSON document containing: context identifier (\texttt{@context}), credential type, UUID, timestamp, issuer metadata, public claims, private claim commitments, Merkle proof path and index, 65-byte EIP-712 signature, and disclosure objects.

\section{Smart Contract Architecture}

\subsection{IssuerRegistry.sol}

\textbf{Responsibility}: Maintains the authoritative on-chain registry of designated university signing keys authorized to issue academic credentials and anchor batches.

\textbf{Design Characteristics}:
\begin{itemize}
    \item Inherits OpenZeppelin \texttt{Ownable2Step}~\cite{OZContracts} for secure, two-phase administrative ownership transfer by university governance.
    \item Maintains active signer states (\texttt{isSigner}) and associated Decentralized Identifiers (\texttt{did}).
    \item Exposes paginated view methods (\texttt{getSigners}, \texttt{getAllSigners}, \texttt{getSignerCount}) for external auditing and verifiers.
\end{itemize}

\textbf{Core Interface}:
\begin{itemize}
    \item \texttt{addSigner(address signer, bytes didLabel)}: Registers an authorized signing address.
    \item \texttt{revokeSigner(address signer)}: Revokes active issuing privileges from a signing address.
    \item \texttt{isSigner(address) $\rightarrow$ bool}: View helper queried by \texttt{CredentialRegistryV3} to authorize batch anchoring and by verifiers during verification.
\end{itemize}

\textbf{Signer Lifecycle and Revocation Consistency}:
In the current prototype implementation, \texttt{IssuerRegistry} enforces a binary authorization flag (\texttt{isSigner}). This design embodies the \textbf{Emergency Kill-Switch Pattern}: if a signing private key is compromised, invoking \texttt{revokeSigner} sets \texttt{isSigner = false}, providing an instantaneous network-wide kill-switch that halts future batch anchoring on \texttt{CredentialRegistryV3} and causes Step~7 of the verification pipeline to reject credentials signed by the compromised key. For routine administrative turnover (e.g., an authorized dean completing their official tenure), decommissioned keys are retired operationally from the active issuance pipeline rather than revoked on-chain, avoiding false-negative rejections of historical diplomas. As formally analyzed in Section~\ref{sec:signer-lifecycle}, decoupling emergency kill-switches from routine personnel turnover will be achieved via on-chain \textbf{Timestamp Validity Windows} correlating the batch anchoring timestamp (\texttt{anchoredAt}) with signer assignment intervals.

\subsection{CredentialRegistryV3.sol}

\textbf{Responsibility}: Serves as the primary decentralized Trust Anchor on Ethereum, persisting batch Merkle roots and managing space-efficient bitmap revocations.

\textbf{Design Characteristics}:
\begin{itemize}
    \item Implements \texttt{Ownable2Step} and \texttt{Pausable} for emergency state-freezing during security incidents without disrupting read-only verification.
    \item Holds an immutable reference to \texttt{IssuerRegistry} to enforce access control via the \texttt{onlySigner} modifier.
    \item Implements storage-optimized 256-bit bitmap revocation: \texttt{mapping(bytes32 $\rightarrow$ mapping(uint256 $\rightarrow$ uint256))}.
\end{itemize}

\textbf{Core Interface}:
\begin{itemize}
    \item \texttt{anchorBatch(merkleRoot, size, ipfsCid)}: Commits a batch Merkle root to blockchain state ($\sim$167,804 gas on Sepolia).
    \item \texttt{revoke(merkleRoot, index)}: Sets the revocation bit for an individual credential within an anchored batch.
    \item \texttt{revokeBatch(merkleRoot, indices[])}: Executes batch revocation across multiple credentials in a single transaction.
    \item \texttt{isRevoked(merkleRoot, index) $\rightarrow$ bool}: View function for deterministic status verification.
    \item \texttt{getAnchor(merkleRoot)}: Fetches batch anchoring timestamp, original issuer address, and cohort size.
\end{itemize}

\textbf{Batch Governance and Revocation Access Control}:
In the smart contract implementation, credential-level revocation is guarded by \texttt{onlySigner} and verifies \texttt{msg.sender == anchor.issuer}. This ensures that individual certificate status cannot be altered by arbitrary third parties. To prevent ``orphaned batches''—a scenario where the original issuing account is decommissioned or rotated, leaving no active signer to manage necessary revocations—the administrative design establishes that the contract owner (\texttt{owner()}, representing the university's central authority) retains supervisory governance to authorize emergency status updates, ensuring institutional continuity across academic generations.

\section{EIP-712 SDK Architecture}

The SDK is organized into 6 modular TypeScript packages:

\subsection{Domain and Type Builder (\texttt{domain.ts})}
Constructs standardized EIP-712 Domain Separators, enforces strict checksummed Ethereum address formats, and exports strongly-typed schema interfaces.

\subsection{Signer and Verifier Modules (\texttt{signer.ts}, \texttt{verifier.ts})}
\begin{itemize}
    \item \textbf{\texttt{signer.ts}}: Generates 65-byte ($r, s, v$) cryptographic signatures using \texttt{wallet.signTypedData()} and recovers public signer addresses via \texttt{ethers.verifyTypedData()}.
    \item \textbf{\texttt{verifier.ts}}: Executes the canonical \textbf{10-Step Verification Pipeline} detailed in Table~\ref{tab:verify-pipeline}.
\end{itemize}

\paragraph{Signer Revocation Semantics and Temporal Consistency}:
Step 7 validates the signing key against the on-chain \texttt{IssuerRegistry}. In the current prototype implementation, this step operates under the \textbf{Emergency Kill-Switch Pattern}: querying \texttt{isSigner(recoveredAddress)} returns a binary boolean flag. If a signing key has been revoked due to a private key compromise, Step 7 immediately halts verification with \texttt{SIGNER\_NOT\_REGISTERED} to protect relying parties from fraudulent issuances. To accommodate routine administrative turnover (where historical credentials must remain permanently valid after an official completes their tenure), Section~\ref{sec:signer-lifecycle} details the formal design of the \textbf{Timestamp Validity Window Pattern}, which correlates the batch anchoring timestamp (\texttt{anchoredAt}, Step 8) with on-chain signer validity intervals.

\subsection{Selective Disclosure and Merkle Utilities (\texttt{disclosure.ts}, \texttt{merkle.ts})}
\begin{itemize}
    \item \textbf{\texttt{disclosure.ts}}: Manages salt generation, salted commitment computation, and selective disclosure filtering for holder presentations.
    \item \textbf{\texttt{merkle.ts}}: Builds OpenZeppelin-compatible Merkle Trees and extracts cryptographic membership proof paths.
\end{itemize}

\section{System Workflow Pipelines}

\subsection{Issuance Workflow (8 Steps)}
\begin{enumerate}
    \item \textbf{CSV Ingestion}: Registrar uploads graduate batch dataset.
    \item \textbf{Validation}: Parser performs runtime type and constraint checking using Zod.
    \item \textbf{UUID Generation}: Generates unique URN identifiers (\texttt{urn:uuid:...}).
    \item \textbf{Commitment Creation}: Generates 256-bit salts and calculates private claim commitments.
    \item \textbf{EIP-712 Signing}: Signs structured payloads with the issuer's private key.
    \item \textbf{Tree Construction}: Builds the Merkle Tree and attaches individual membership proofs.
    \item \textbf{On-Chain Anchoring}: Submits \texttt{anchorBatch(merkleRoot, size, ipfsCid)} to Sepolia.
    \item \textbf{Persistence}: Stores batch and credential records in PostgreSQL via Prisma.
\end{enumerate}

\subsection{Verification Workflow}
Executed in three distinct stages: Offline structural verification (Steps 1--6), Online blockchain state attestation (Steps 7--9), and temporal expiration validation (Step 10).

\subsection{Revocation Workflow}

Revocation is structured across two distinct operational scopes:
\begin{enumerate}
    \item \textbf{Credential-Level Revocation}: When an individual degree is revoked (e.g., academic misconduct or administrative cancellation), the issuing authority executes \texttt{revoke(merkleRoot, index)} or \texttt{revokeBatch(merkleRoot, indices[])} on \texttt{CredentialRegistryV3}. The transaction flips the targeted bit in the 256-bit bitmap mapping (\texttt{\_revocationBitmap[merkleRoot][wordIndex] |= bitMask}), incurring a warm SSTORE cost of $\sim$5,000 gas. Subsequent verification queries at Step 9 instantly detect the revocation via \texttt{isRevoked()}.
    \item \textbf{Signer-Level Authorization Revocation (Emergency Kill-Switch)}: When a signing key is suspected of private key leakage or compromise, university administration invokes \texttt{revokeSigner(signerAddress)} on \texttt{IssuerRegistry.sol}. Under the current prototype architecture, this acts as an immediate emergency kill-switch: it strips batch anchoring privileges on \texttt{CredentialRegistryV3} and causes Step~7 of the verification pipeline to reject credentials signed by the compromised key. For routine administrative turnover (e.g., an authorized dean completing their tenure), decommissioned keys are retired from the institution's active signing queue without invoking the on-chain kill-switch, preserving historical diploma validity until the smart contract is extended with timestamp validity windows (Section~\ref{sec:signer-lifecycle}).
\end{enumerate}

\section{Database Schema Modeling (Prisma ORM)}

The Phase 3 schema defines four normalized relational entities:
\begin{itemize}
    \item \textbf{\texttt{BatchV3}}: Persists batch identifiers, anchored Merkle roots, cohort sizes, transaction hashes, and on-chain timestamps.
    \item \textbf{\texttt{CredentialV3}}: Stores individual credential UUIDs, batch indices, public claims, EIP-712 signatures, Merkle proof paths, and serialized JSON documents.
    \item \textbf{\texttt{DisclosureV3}}: Records individual salted attribute components (\texttt{salt}, \texttt{key}, \texttt{value}, \texttt{commitment}) mapped 1-to-many from \texttt{CredentialV3}.
    \item \textbf{\texttt{RevocationV3}}: Maintains an immutable audit trail of revocation events mirroring the on-chain state.
\end{itemize}

Schema tables use the \texttt{\_v3} suffix, enabling seamless coexistence with Phase 2 data without schema migrations or conflicts.
