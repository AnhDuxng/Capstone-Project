\end{itemize}

All \textbf{33 out of 33 security attack simulations were successfully thwarted}, demonstrating robust tamper resistance.

\section{Architectural Ablation Study and Performance Attribution}
\label{sec:ablation-study}

To quantitatively determine the specific performance contribution of each architectural component and directly address the question of \textit{which core technique fundamentally determines the system's operational viability and performance profile}, an architectural ablation study was conducted. We systematically decomposed the BK Credential System into its constituent modules and evaluated four progressive architectural configurations under an identical university cohort workload of $N = 10{,}000$ credentials:

\begin{itemize}
    \item \textbf{Configuration 1 (Pure On-Chain NFT Baseline / ERC-721)}: Represents legacy blockchain architectures where each certificate is minted as an individual non-fungible token on-chain, storing metadata directly or referencing IPFS URIs.
    \item \textbf{Configuration 2 (EIP-712 Off-Chain Signing + Individual On-Chain Anchoring)}: Applies EIP-712 off-chain typed signing to separate payload creation from state execution, but commits each credential hash individually to the blockchain registry without cryptographic batching ($\mathcal{O}(N)$ on-chain transactions).
    \item \textbf{Configuration 3 (EIP-712 + Merkle Tree Batching + Conventional Mapping Revocation)}: Combines off-chain signing with Merkle tree batching to commit a single 32-byte Merkle root on-chain ($\mathcal{O}(1)$), but retains a conventional per-credential storage mapping (\texttt{mapping(bytes32 => bool)}) for revocation.
    \item \textbf{Configuration 4 (Full Proposed Architecture / Phase 3)}: Integrates all four proposed pillars: EIP-712 off-chain signing, cryptographic Merkle tree batching, 256-bit bitmap revocation, and 256-bit salted-hash selective disclosure commitments.
\end{itemize}

\subsection{Key Technical Findings and Performance Attribution}

From the quantitative results presented in Table~\ref{tab:ablation-study}, several definitive architectural insights emerge regarding the technical core of this Capstone Project:

\begin{enumerate}
    \item \textbf{The Core Performance Pillar: Cryptographic Merkle Tree Batching with EIP-712}:
    Comparing Configuration 2 with Configuration 3 demonstrates that \textbf{Merkle Tree Batching combined with EIP-712 Off-Chain Signing is the single most decisive technique that shapes the entire project's viability}. 
    \begin{itemize}
        \item While EIP-712 off-chain signing successfully eliminates signature verification overhead from the consensus layer, committing individual credentials still incurs an unsustainable linear cost ($\mathcal{O}(N)$ transactions, $\sim$240 million gas for 10,000 graduates).
        \item Introducing Merkle Tree batching collapses on-chain state registration into a single $\mathcal{O}(1)$ transaction of 167,804 gas, driving an immediate \textbf{99.93\% reduction in on-chain gas expenditure} (from $\sim$24,638 gas down to 16.78 gas per student).
        \item Furthermore, Merkle batching decouples student credential generation from Ethereum block gas limits, elevating overall cohort issuance throughput from $\sim$30 creds/s to \textbf{809.1 credentials/second}.
    \end{itemize}
    
    \item \textbf{Secondary Optimization: 256-bit Bitmap Revocation Matrix}:
    Comparing Configuration 3 with Configuration 4 highlights the operational role of the bitmap revocation model.
    \begin{itemize}
        \item While Merkle batching optimizes issuance, standard revocation mappings (\texttt{mapping(bytes32 => bool)}) still require a full 32-byte EVM storage slot (\texttt{SSTORE}, $\sim$22,100 gas) for every invalidated diploma. Revoking 100 credentials would require 100 separate storage writes ($\sim$2.21 million gas).
        \item By packing 256 credential revocation states into a single \texttt{uint256} storage word, our bitmap design permits revoking up to 256 credentials within the same word in a single transaction consuming only $\sim$90,000 gas. This yields a \textbf{24.5$\times$ gas reduction for batch revocations} and reduces state bloating on the Ethereum ledger by up to \textbf{256$\times$}.
    \end{itemize}

    \item \textbf{Privacy-Efficiency Trade-off: Salted-Hash Commitments vs. Zero-Knowledge Proofs}:
    Configuration 4 proves that the 256-bit salted-hash commitment scheme offers the optimal engineering compromise for academic credentials. Whereas advanced Zero-Knowledge Proof schemes (zk-SNARKs / zk-STARKs) introduce significant client-side cryptographic proving latency (typically 500~ms to 2,000~ms) and require expensive on-chain pairing verification (200k--300k gas), our salted-hash approach executes in \textbf{under 0.1~ms} on commodity browser hardware, achieving practical, privacy-preserving selective disclosure with zero on-chain verification gas penalty.
\end{enumerate}

In summary, this ablation analysis confirms that while Bitmap Revocation and Salted-Hash Commitments contribute substantial secondary storage and privacy optimizations, \textbf{Merkle Tree Batching coupled with EIP-712 Off-Chain Signing constitutes the foundational core of the BK Credential System}, fundamentally enabling scalable, university-wide deployment on public Ethereum networks.
